## 1. "AUC 0.90은 너무 높지 않나요? 과적합 아닌가요?"

**예상 질문 형태**
- "Test AUC가 0.90이면 실제 서비스에서도 같은 성능이 나올 것이라고 보나요?"
- "훈련/테스트 분리가 제대로 됐나요?"
- "데이터 리키지 가능성은 없나요?"

**답변 요지**

1. **그룹 분리 적용**: `USER_KEY` 기준으로 그룹 분리(GroupStratifiedKFold)를 적용해 동일 사용자의 레코드가 훈련/테스트에 동시에 등장하지 않도록 설계했습니다. 사용자 단위 리키지는 구조적으로 차단되어 있습니다.

2. **w1_4 AUC 0.90은 보수적으로 해석**: w1_4 윈도우(0-27일)는 구독 만료에 가까운 시점까지 행동 데이터를 포함합니다. 이탈 직전 행동 패턴이 반영될 수 있어 0.9037은 낙관적 상한으로 봅니다. 실운영 기준으로는 w1_3(0-20일) 모델의 [PLACEHOLDER: confirmed AUC after 02b]을 권장합니다.

3. **다중 감사 단계 실시**: Stage 06b~06h에서 오버피팅 탐지, 피처 중요도 안정성, 타겟 리키지 여부를 별도 감사했습니다. 현재까지 명확한 리키지 신호는 발견되지 않았습니다.

4. **솔직한 한계 인정**: 실서비스 배포 시 covariate shift(시간적 분포 변화)로 성능이 하락할 수 있습니다. 현재 결과는 동일 기간 내 hold-out 평가이며, 미래 코호트 대상 성능은 보장되지 않습니다.

## 2. "전처리가 미흡한 것 아닌가요?"

**예상 질문 형태**
- "나이=40, 성별=N 처리는 어떻게 했나요?"
- "iOS 결제 사용자는 왜 따로 구분했나요?"
- "구독 종료 이후 시청 기록은 어떻게 처리했나요?"

**답변 요지**

1. **age=40 / gender=N 이슈**: 약 17%의 미인증 사용자가 age=40, gender=N 기본값을 가집니다. 이를 실제 40세/무성별로 해석하면 분석이 왜곡됩니다. Stage 02b(forensic audit)에서 이 집단의 특성과 타겟 분포를 별도 검증하고, 필요 시 인구통계 피처를 선택적으로 제거하거나 결측값 플래그를 추가합니다.

2. **iOS 결제 사용자**: App Store 청구 특성상 결제 정보가 불완전할 수 있습니다. 이 집단은 `billing_method` 피처로 식별되며, 인구통계 불확실성과 교차 분석됩니다.

3. **구독 종료 후 시청 기록 (5,740건)**: 데이터 오류 또는 정책 예외(grace period)로 발생한 것으로 추정됩니다. Stage 03에서 관측 윈도우를 구독 기간 내로 제한하여 피처 생성 시 이 기록들은 자동으로 제외됩니다.

4. **현재 상태**: Stage 02b가 완료되기 전까지 전처리 정책이 일부 변경될 수 있습니다. 이 점을 명시하고 있으며, 모든 downstream 결과는 PROVISIONAL 표시를 유지합니다.

## 3. "다중공선성 문제는 없나요?"

**예상 질문 형태**
- "비슷한 피처가 너무 많은 것 아닌가요?"
- "VIF를 확인했나요?"
- "피처 간 상관관계가 높으면 모델 해석이 어렵지 않나요?"

**답변 요지**

1. **감사 실시**: Stage 06d에서 피처 간 상관관계 행렬과 클러스터링을 통해 중복 피처 군을 식별했습니다. Stage 05e에서 최종 피처 프루닝 정책을 수립했습니다.

2. **트리 기반 모델의 특성**: LightGBM, HistGradientBoosting 등 트리 계열 모델은 다중공선성에 상대적으로 강건합니다. 다중공선성은 주로 회귀계수 해석 시 문제이며, 예측 성능에는 직접적 영향이 제한적입니다.

3. **해석 모델 분리**: LogisticRegression은 해석 목적으로만 활용하며, 해당 모델에서는 상관관계 높은 피처를 사전 제거한 피처셋을 사용합니다.

4. **SHAP에서의 주의**: 상관된 피처 간 SHAP 값은 분산될 수 있습니다. 개별 피처 SHAP보다 피처 그룹(사용 피처군, 콘텐츠 피처군) 단위의 기여도로 해석합니다.

## 4. "SHAP 값을 인과관계로 해석하면 안 되지 않나요?"

**예상 질문 형태**
- "SHAP이 높다고 해서 그게 이탈 원인이라고 할 수 있나요?"
- "이 피처를 개선하면 이탈이 줄어드나요?"

**답변 요지**

1. **명확한 구분**: SHAP은 "이 피처가 모델 예측에 얼마나 기여했는가"를 설명합니다. 이는 **예측 기여도(predictive contribution)**이며, **인과 효과(causal effect)**가 아닙니다.

2. **금지 표현**: "A가 이탈을 유발했다", "A를 개선하면 이탈이 감소한다"와 같은 표현은 사용하지 않습니다. → [상세 가이드: `claim_wording_guardrail_v2.md`]

3. **허용 표현**: "A 피처는 이탈 예측 모델에서 높은 관련성을 보였다", "A가 낮은 사용자 집단에서 이탈률이 관찰상 더 높다"

4. **교란변수 가능성**: 예를 들어 시청 횟수가 낮으면 이탈 확률이 높게 예측되더라도, 이는 관심 감소→시청 감소→이탈의 경로일 수 있으며, 시청 자체를 늘리는 개입이 이탈을 막을 것이라고 단정할 수 없습니다.

## 6. "왜 Stage 02b forensic audit이 별도로 필요한가요?"

**배경**

Stage 02(전처리 정책)는 명백한 중복 제거와 타겟 충돌 해소에 집중했습니다. 그러나 다음 질문들은 별도의 심층 감사 없이는 답하기 어렵습니다.

**02b가 필요한 이유**

1. **age=40 집단의 실체**: 이 집단이 단순 기본값인지, 아니면 특정 가입 경로(예: 가족 계정, 기업 계정)인지 확인이 필요합니다. 타겟 분포가 다르다면 인구통계 피처 사용 자체를 재검토해야 합니다.

2. **iOS 결제 사용자 특성**: billing_method별 인구통계 분포, 타겟 비율이 일반 사용자와 유의미하게 다를 경우 별도 피처 처리가 필요합니다.

3. **전처리 후 공식 row count 확정**: 현재 23,933이라는 수치는 Stage 02 기준이지만, 02b에서 추가 제외 조건이 생기면 downstream 모든 수치(피처, 모델 성능, 세그먼트 크기)가 변경됩니다.

4. **공식 수치 근거 확보**: 발표 및 보고서에서 인용하는 모든 수치는 02b 완료 후 확정된 값이어야 합니다. 현재 결과는 preliminary이며, 이를 명시하는 것이 학술/업무 신뢰도를 보호합니다.

**02b 완료 전 upstream 재실행 필요 범위**

Stage 02b → 03 → 04 → 05 → 06 → 07 → 08 → 09 순으로 재실행이 필요합니다. 이 때문에 현재 모든 수치는 PROVISIONAL입니다.
